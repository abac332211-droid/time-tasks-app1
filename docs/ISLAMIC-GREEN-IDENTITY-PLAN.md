# خطة الهوية الخضراء الإسلامية — TimeTasks

> **الحالة:** خطة معتمدة للتوثيق والتحضير فقط. التنفيذ البصري لم يبدأ.  
> **تاريخ تثبيت مرجع الحالة:** 22 نوفمبر 2026.  
> **النطاق:** توثيق متطلبات المرحلة المستقبلية دون تغيير واجهة التطبيق أو سلوكه.

## 1. الهدف والمبدأ الحاكم

تطوير هوية خضراء إسلامية هادئة وأنيقة لتطبيق TimeTasks، مع الحفاظ على استقرار الوظائف الحالية. التنفيذ المستقبلي تدريجي ومحصور في CSS، ولا يبدأ قبل اجتياز بوابات النسخة الأساسية والاستقرار والتباين.

**المبدأ الحاكم:** لا نغيّر سلوكًا مستقرًا أو بنية التطبيق للحصول على تحسين جمالي. أي مطلب بصري لا يمكن تحقيقه ضمن القيود المعتمدة يُرفع للمراجعة بدل الالتفاف على القيود.

## 3. توضيح نطاق PR #7 — لا تقتصر مراجعته على الألوان

مراجعة الفرق الكامل لـ PR #7 تُظهر أن التغييرات في `index.html` تشمل أكثر من قيم الألوان. وهي تتضمن:

- متغيرات حدود عناصر التحكم في الوضعين، وتغييرات حدود حقول الإدخال والأزرار الثانوية.
- متغيرات هندسية مشتركة للمسافات الداخلية للبطاقات والفواصل وارتفاعات عناصر التحكم ومقادير التركيز.
- إحلال المتغيرات محل قيم ثابتة في ارتفاعات الأزرار والحقول والتبويبات وبعض عناصر التحكم.
- تعديل إزاحة وحدود مؤشرات التركيز.
- قصر تأثير الضغط المرئي على الأزرار غير المعطلة.
- إزالة خفض العتامة عن المهام والمشاريع المكتملة، وتعديل أسلوب إظهار عناصر checklist المكتملة.
- إعادة تنظيم أزرار المؤقت، بما في ذلك العرض والارتفاع والحد الأدنى للعرض و`white-space: nowrap`.
- إضافة حالات تحويم لمجموعات التصفية والتبويبات وأزرار التقييم والطاقة والتنقل.
- تعديلات أخرى على الحدود وأنصاف الأقطار وتوحيد أسلوب عناصر التحكم.

وبناءً عليه، يجب أن تتضمن بوابة اعتماد PR #7 مراجعة **كل هذه الفئات** في الوضعين الفاتح والداكن وعلى المقاسات المستهدفة، وليس مراجعة درجات اللون وحدها.

## 4. بوابات التنفيذ وترتيبها الإلزامي

### المرحلة 0 — تثبيت النسخة الأساسية وإغلاق متطلبات P0

لا يبدأ العمل على الهوية قبل استكمال هذه المرحلة.

1. إعداد قائمة صريحة بمتطلبات P0 من مصدرها المعتمد؛ لا تُنشأ قائمة افتراضية ولا يُفترض إغلاق متطلب دون دليل.
2. لكل متطلب P0 يُسجل: المعرّف، وصف الخطر، معيار الإغلاق، Commit المختبَر، رابط الاختبار أو الدليل، النتيجة، والمراجع.
3. مراجعة PR #6 على رأسه الفعلي وقت الاعتماد، والتحقق من أن نتائج CI تخص هذا الرأس لا رأسًا تاريخيًا أو مرشح دمج مختلفًا.
4. التحقق من وجود مراجعة مستقلة مناسبة على الرأس الذي سيُعتمد، وعدم اعتبار نجاح الاختبارات الآلية موافقة مستقلة.
5. إكمال أي اختبار ميداني مطلوب للاستقرار، بما يشمل سيناريوهات Android الفعلية ذات الصلة بالتخزين والاستعادة والتنبيهات والمؤقت، وفق قائمة اختبار موثقة.
6. مراجعة PR #7 بالكامل كما ورد في القسم السابق، والتحقق من أثر تغييرات التحكم والمسافات والمؤقت والحالات المكتملة، إلى جانب التباين.
7. إتمام المعاينة البصرية للوضعين الفاتح والداكن، وتسجيل الجهاز/المتصفح/العرض/Commit وصور المعاينة.
8. توثيق قرار بوابة المرحلة صفر: **مقبول** أو **مرفوض مع أسباب محددة**.

لا تُغلق البوابة اعتمادًا على عدد الاختبارات وحده. وأي متطلب P0 بلا دليل إغلاق يبقى مفتوحًا.

### المرحلة 1 — تثبيت نقطة الأساس وعلاقة الفروع

بعد اجتياز المرحلة صفر فقط:

- تحديد SHA واحد صريح للنسخة الأساسية المعتمدة، وتسجيل سبب اختياره.
- إذا كانت PR #6 وPR #7 قد دُمجتا واعتمدتا، يبدأ فرع التنفيذ من آخر Commit معتمد يتضمن التغييرات المقبولة.
- إذا بقيت الطلبات مفتوحة وغير مدمجة، يُحدد تسلسل الاعتماد صراحةً: قاعدة الهوية تكون آخر رأس مقبول من سلسلة الاعتماد، ويُجعل PR الهوية متسلسلًا على الفرع الصحيح بدل الادعاء بأنه مستقل عن تغييرات لم تُدمج.
- استقلال العمل يعني استقلال نطاق التغييرات وطلب المراجعة؛ ولا يعني تجاهل اعتماد PR #7 على PR #6.
- لا يُنشأ فرع التنفيذ الفعلي قبل اعتماد نقطة الأساس. وفرع هذه الوثيقة الحالي فرع توثيقي فقط، وليس فرع تنفيذ الهوية.

### المرحلة 2 — جرد متغيرات CSS وبناء خريطة الألوان

**لا تُنشأ منظومة متوازية للمتغيرات.**

1. جرد جميع متغيرات CSS الموجودة ومواقع تعريفها واستخداماتها، بما فيها متغيرات الأساس والعلامة التجارية والحالات والسطوح والحدود والهندسة والتركيز.
2. إعداد جدول يربط كل متغير حالي بوظيفته ومستهلكيه وقيمته في الوضع الفاتح والداكن.
3. الإبقاء على أسماء المتغيرات الحالية عندما تؤدي الغرض نفسه.
4. إضافة المتغيرات الدلالية الناقصة فقط. وعند الحاجة إلى اسم جديد، يُربط بالمتغير القديم المناسب أو يُعتمد انتقال واضح؛ ولا يُترك متغيران متعارضان لنفس الدور.
5. في خطوة الجرد والمواءمة الأولى لا يتغير المظهر المرئي ولا سلوك العناصر. بعدها يجري تبني المتغيرات تدريجيًا مع كل جزء من الأجزاء الخمسة.
6. تُختبر كل قيمة على الخلفية الفعلية التي ستستخدم فوقها، وليس على الأبيض وحده.

### المرحلة 3 — تطبيق الهوية تدريجيًا على خمسة أجزاء

الترتيب ملزم، ويُراجع كل جزء قبل الانتقال إلى الذي يليه:

1. **رأس التطبيق:** هوية خضراء أنيقة، عنوان واضح، وتباين مناسب.
2. **الأزرار:** توحيد اللون الرئيسي والثانوي وحالات التركيز والضغط والتعطيل دون تغيير آلية النقر أو أبعاد التخطيط المعتمدة.
3. **البطاقات:** أسطح وحدود هادئة، مع الحفاظ على بنية البطاقة وأبعادها الحالية؛ وأي تغيير هندسي يُعرض منفصلًا للموافقة.
4. **المهام:** تمييز الحالة النشطة والمكتملة دون خفض وضوح النص، وعدم الاعتماد على اللون وحده.
5. **المؤقت:** إبراز الوقت وأزرار التحكم والحالة بوضوح، دون تغيير دورة المؤقت أو سلوكه أو ترتيب عناصر التحكم.

### المرحلة 4 — الاختبار الشامل والمراجعة

تُنفذ جميع اختبارات القسمين 7 و8، وتُعالج الملاحظات ضمن نطاق CSS المصرح به. كل إصلاح له Commit واضح ودليل قبل/بعد ونتيجة اختبارات.

### المرحلة 5 — الاعتماد النهائي

- مراجعة مستقلة للفرق الكامل.
- عرض صور قبل/بعد وسجل الاختبارات.
- مراجعة المستخدم النهائية للمعاينات.
- لا دمج ولا نشر ولا إصدار ولا تعديل لـ `main` إلا بموافقة صريحة منفصلة.

## 5. لوحة الألوان المرجعية

هذه قيم مرجعية للهوية وليست تصريحًا باستخدامها دون اختبار التباين:

| الدور | اللون | الاستخدام المقصود |
|---|---|---|

| الأخضر الداكن | `#14382d` | حالات التفاعل والضغط |
| الخلفية الفاتحة | `#f4f7f4` | خلفية الوضع الفاتح |
| الذهبي | `#d4af37` | لمسات زخرفية محدودة |

ضوابط التطبيق:

- يُستخدم الذهبي باعتدال، ولا يُستخدم نصًا صغيرًا أو لونًا وحيدًا لأيقونة أو مؤشر حالة يحتاج إلى وضوح.
- تباين الذهبي مع الأبيض يقارب 2.1:1؛ لذلك لا يعتمد للنصوص الصغيرة على خلفية بيضاء.
- تُحدد درجات النص والسطوح والحدود للفاتح والداكن بعد قياس التباين على الأزواج الفعلية.
- لا تُفترض قيمة أخضر واحدة صالحة للنصوص والأسطح والحدود في كل الحالات.

## 6. الخطوط

- يُستخدم Amiri للعناوين المناسبة فقط إذا كان متاحًا في المشروع أو ضمن الأصول المعتمدة.
- تُحافظ النصوص الكثيفة والأرقام وحقول الإدخال على خط واضح ومريح ومناسب للقراءة.
- لا تُضاف مكتبة أو إطار عمل أو طلب خط خارجي جديد دون قرار وموافقة منفصلين.
- إذا لم يكن Amiri متاحًا، يستخدم بديل مناسب مؤقتًا بدل إدخال اعتماد جديد تلقائيًا.

## 7. معايير الوصول والتباين

تُراجع الألوان وفق WCAG 2.2 AA حيث ينطبق:

- النص العادي: نسبة تباين لا تقل عن **4.5:1**.
- النص الكبير: نسبة تباين لا تقل عن **3:1**.
- حدود عناصر التحكم والمؤشرات الرسومية اللازمة لفهم العنصر أو حالته: نسبة تباين لا تقل عن **3:1** مقابل اللون المجاور ذي الصلة، وفق معيار WCAG 2.2 رقم 1.4.11.
- لا يكون اللون الوسيلة الوحيدة لعرض حالة المهمة أو المؤقت؛ يجب أن توجد علامة أخرى ظاهرة ومفهومة، مثل رمز أو نص أو خط أو اختلاف شكل متاح أصلًا.
- يُتحقق من مؤشر التركيز المرئي وعدم حجبه في حالات التنقل بلوحة المفاتيح.
- تُسجل نتائج القياس لكل زوج ألوان مهم، مع تسمية الوضع والخلفية وعنصر الواجهة.

## 9. القيود البرمجية وحدود التعديل

### المسموح

- تعديل قواعد CSS الموجودة فقط.
- إذا كانت القواعد داخل `index.html`، يكون التعديل محصورًا داخل كتلة `<style>`.
- تعديل قيم المتغيرات أو قواعد الألوان والحدود والطباعة المصرح بها، مع الاحتفاظ بالبنية الحالية.
- إضافة متغيرات CSS دلالية ناقصة بعد الجرد والمواءمة.

### غير المسموح

- لا تعديل على JavaScript أو معالجات الأحداث أو دوال المهام والمؤقت.
- لا تعديل على عناصر DOM أو ترتيبها أو خصائص HTML أو السمات أو النصوص البنيوية.
- لا تعديل على مفاتيح التخزين أو آليات الحفظ والاستعادة أو التنبيهات.
- لا إضافة Tailwind أو إطار عمل أو مكتبة أو اعتماد خارجي.
- لا تعديل على `display` أو `visibility` أو `pointer-events` أو `position` أو `z-index` أو بنية Flex/Grid أو سلوك التمرير أو استقبال النقرات.
- لا تغيير في أبعاد التخطيط أو أحجام عناصر التحكم أو المسافات الهندسية لمجرد التحسين الجمالي. إذا ظهر خلل فعلي قابل لإعادة الإنتاج، يوثق بدليل ويطلب له إذن منفصل قبل تغييره.
- لا مؤثرات أو حركات إضافية غير لازمة، ولا زخارف أو ذهبي مفرط.
- لا دمج أو نشر أو إصدار أو تغيير `main`.

**قاعدة تدقيق ملف `index.html`:** قد يظهر الملف ضمن قائمة الملفات المعدلة لأن CSS موجود داخله؛ هذا مقبول فقط إذا أثبت فحص الفرق أن التغييرات داخل كتلة CSS وحدها. وجود الملف في الفرق لا يجيز تعديل HTML أو DOM أو JavaScript.

## 10. إدارة الفروع والـ Commits وطلبات المراجعة

- تُنشأ لاحقًا فرع تنفيذ مستقل من SHA الأساس المعتمد بعد إغلاق المرحلة صفر.
- لا يُستخدم فرع PR #7 لتطوير الهوية، ولا تُضاف تغييرات الهوية إلى PR #7.
- يكون PR الهوية مستقلًا في نطاقه، مع توثيق قاعدة الفرع وعلاقة الاعتماد إذا كانت PR #6 وPR #7 لم تُدمجا بعد.
- تُنفذ كل دفعة من الأجزاء الخمسة في Commit واضح وقابل للتراجع.
- بعد كل دفعة: مراجعة diff، فحص أن الملفات والتغييرات ضمن النطاق، اختبارات الانحدار، وصورة معاينة.
- PR الهوية يبقى Draft إلى حين اكتمال المراجعة والاختبارات؛ ولا يُدمج دون موافقة المستخدم.
