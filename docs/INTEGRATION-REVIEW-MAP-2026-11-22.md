هذا يدعم إغلاق فجوة F-01 على هذا الرأس تحديدًا، ولا يعني إغلاق جميع ثغرات P0 أو اعتماد الإصدار.

## 4. ما نعرفه وما لم يُحسم

### حقائق تحققنا منها

1. خط الأساس `main` هو commit المذكور أعلاه، وإصدار `package.json` فيه 2.8.8.
2. PR #6 عند الرأس `38d27c...`، مفتوح بوضع Draft، ويمثل 294 commit فوق main.
3. Release Hardening عند الرأس `2d8b946...`، وهو امتداد مباشر لـPR #6 يضيف 21 commit.
4. Release Hardening يضيف فحص Browser Security مستقلًا في الـworkflow، وقد نجح تشغيل CI المحدد أعلاه.
5. PR #4 مسار بصري مستقل يغيّر CSS وWorkflow، ويحتاج معالجة تداخل قبل أي جمع.

### أمور لم يثبتها هذا الجرد

- لم تُراجع قائمة كل 294 commit وكل 315 commit واحدةً واحدة في هذه الوثيقة.
- لم تُرفق قائمة SHA كاملة للـ21 commit مع خريطة اعتماديات على مستوى الوظائف والكتل داخل `index.html`.
- تصنيف مجموعات الـ21 commit هو تصنيف أولي، لا إثبات أن المجموعات مستقلة أو قابلة للنقل المنفصل.
- نجاح GitHub Actions لا يثبت سلامة التطبيق بصريًا أو ميدانيًا على كل أجهزة Android.
- إغلاق F-01 لا يساوي إغلاق جميع ملاحظات P0.
- المراجعة المسجلة كـCOMMENTED على PR #6 من حساب مالك المستودع نفسه لا تثبت وجود مراجع مستقل بهوية مختلفة. يجب طلب مراجعة مستقلة حقيقية على المرشح النهائي.
- لم يُتحقق إداريًا بصورة حاسمة من كل إعدادات حماية الفروع وبيئة إصدار Android.
- لم يثبت هنا تطابق شهادة توقيع APK النهائي مع شهادة التوقيع الأصلية المتوقعة.

## 5. خيارات التكامل — ليست قرارات تنفيذية

### الخيار الأول: الحفاظ على السلسلة كاملة

إذا قُبلت جميع تغييرات PR #6 والـ21 commit الإضافية في Release Hardening بعد مراجعتها، فالعلاقة المباشرة بين الفرعين تسمح من حيث تاريخ Git بالتفكير في تحريك فرع PR #6 إلى رأس Release Hardening بطريقة fast-forward. هذا يحافظ على تاريخ commits ولا يختار تغييرات من عناوينها فقط.

لكن ذلك **ليس توصية بالدمج الآن**، ولا إذنًا لتحديث الفرع. يلزم أولًا اعتماد جميع التغييرات وفحصها على الرأس النهائي.

### الخيار الثاني: انتقاء مجموعات محددة

إذا رُفضت بعض التغييرات أو أُريد فصل مجموعات، فيلزم إنشاء خريطة على مستوى commit والوظيفة والكتل البرمجية، ثم مراجعة الاعتماديات والاختبارات قبل أي نقل انتقائي. هذا المسار أكثر حساسية لأن `index.html` يجمع HTML وCSS وJavaScript في ملف واحد؛ وانتقاء أجزاء منه بناءً على عناوين commits وحدها مخاطرة.

### التعامل مع PR #4

يبقى منفصلًا إلى أن يُحسم نظام الألوان النهائي، وتُحل إعادة تعريف متغيرات CSS، وتُراجع تغييرات Workflow في ضوء سلسلة Stability/Hardening.

## 6. بوابات ما قبل الدمج أو الإصدار

لا يُعد أي فرع جاهزًا للدمج أو الإصدار حتى تُغلق هذه البوابات على **SHA نهائي واحد**:

1. نشر manifest كامل للـ21 commit مع SHA والتصنيف ووصف الأثر والاعتماديات، ثم مراجعة محتوى كل مجموعة.
2. مراجعة مستقلة من حساب GitHub مختلف عن مالك المستودع، مرتبطة بالرأس النهائي نفسه.
3. مراجعة أمنية شاملة لملاحظات P0 ونتائج Browser Security على الرأس النهائي؛ لا يكفي الاعتماد على فحص قديم أو على نجاح CI وحده.
4. اختبارات Android على أجهزة فعلية تشمل Doze وForce Stop وإعادة التشغيل واستعادة بيانات مستخدم سابقة والإشعارات ومؤقت التركيز.
5. اختبار تكامل بين المهام والمشاريع وحذف المشروع والنسخ الاحتياطي والاستعادة والمهام المتكررة والإشعارات والمؤقت وفشل التخزين.
6. التحقق إداريًا من حماية الفروع وبيئة `android-release` وإعدادات الأسرار، دون كشف قيم الأسرار.
7. التحقق من مفتاح توقيع Android الأصلي وبصمة شهادة SHA-256 المتوقعة عبر APK إصدار موقّع؛ لا يكفي نجاح بناء Debug.
8. توحيد رقم الإصدار إلى 2.9.1 فقط بعد تثبيت المرشح النهائي، ثم إعادة الاختبارات والبناء على النسخة المحددة.
9. إبقاء طلبات السحب Draft إلى أن تكتمل شروط المراجعة. وأي قرار دمج أو إصدار يحتاج موافقة صريحة منفصلة.
