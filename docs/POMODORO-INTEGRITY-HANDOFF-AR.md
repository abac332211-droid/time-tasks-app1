## 4. نتائج التدقيق المثبتة في `index.html` بفرع PR #13

كل أرقام الأسطر في هذا القسم تخص فقط الملف عند commit `109d40d2a51425f3762480b59cd703088057e591`. أعد تحديدها بعد أي تعديل.

### 4.1 `saveData()` ما زالت متزامنة

- تعريف `function saveData()` عند السطر 3982.
- تعيد قيمة منطقية فوراً (`true/false`)؛ لا تعيد Promise.
- قراءة `STORAGE_KEY` تبدأ قرب السطر 4028.
- فحص خط الأساس المتفائل قرب 4034–4037.
- تجهيز سجل V2 وإعادة التحقق قرب 4083–4095.
- إعادة قراءة المفتاح قبل الكتابة قرب 4099–4106.
- الكتابة الفعلية إلى `STORAGE_KEY` عند 4108.
- فحص القراءة بعد الكتابة وتحديث خط الأساس بعد ذلك.
- لا تكتسب الدالة نفسها Web Lock، ولا تثبت ملكية القفل قبل قراءة-تحقق-كتابة سجل المهام.

عدد مستدعي `saveData()` في هذا الملف هو **21 موضعاً** (بعد استبعاد تعريف الدالة). مواقع الاستدعاء:

`2179, 2227, 2366, 3161, 4164, 5180, 5565, 5845, 5976, 5990, 6086, 6131, 6148, 6182, 6215, 12245, 12393, 12750, 13961, 14134, 14210`.

هذه القائمة أحدث من رقم 20 الوارد في تقرير خط الأساس؛ اختلافها متوقع لأن تقرير خط الأساس السابق استند إلى SHA أقدم. عند تحويل الحفظ إلى async يجب إعادة جرد الاستدعاءات في المصدر الجديد، وعدم الاعتماد على هذه القائمة وحدها.

أخطر خطأ ممنوع عند التحويل:
```js
if (saveData()) { /* success */ }
```
إذا أصبحت `saveData()` تعيد Promise، فالكائن Promise truthy قبل اكتمال الحفظ. يجب أن يصبح المستدعي `await saveData()` أو يعالج Promise صراحة، ولا يعرض نجاحاً ولا يغلق النموذج ولا يغير الواجهة إلى حالة «محفوظ» قبل القراءة والتحقق الفعليين.

### 4.2 القفل الحالي لا يغطي كل كتّاب المهام

- القفل الموجود هو `_withStopwatchTransactionLock(callback)` قرب السطر 12423.
- اسم Web Lock الفعلي: `timeTasksApp-stopwatch-transaction`، حصري `mode: "exclusive"`.
- عند التداخل داخل نفس سياق الصفحة، يستخدم `_stopwatchTransactionLockDepth` لإعادة استخدام ملكية القفل المحلية بدلاً من طلب القفل مرة أخرى.
- عند غياب Web Locks يرفض هذا الغلاف العملية بـ Promise rejection.
- هذا القفل يخدم مسارات معاملات Stopwatch/الاسترداد المتعاونة، وليس جميع استدعاءات الحفظ في التطبيق.
- `_storageWriteAllowed()` قرب 1738 يفحص أعلام الحظر وخط الأساس وبعض علامات الاسترداد؛ لكنه لا يثبت بذاته أن المستدعي يملك Web Lock.
- `_saveSessions()` قرب 11259 يستدعي `_storageWriteAllowed()` ثم يكتب عبر `_writeSecondaryStorageVerified()`، ولا يطلب القفل بنفسه.
- `saveData()` لا تفرض وجود `_stopwatchTransactionLockDepth > 0`.

**النتيجة:** فحص baseline/Storage events كشف تعارض متفائل، وليس قفلاً حصرياً يغطي كامل الفترة بين القراءة والكتابة. كما أن Web Locks ينسق الكتّاب المتعاونين فقط؛ المسارات التي لا تدخل القفل تبقى سباقاً قائماً.

### 4.5 `actualSeconds` أضيف إلى الفاحص، لا إلى دورة حياة الرصيد

في فرع PR #13، جميع مراجع الحقول الأربعة التالية في `index.html` تقع داخل فاحص الحقول تقريباً عند 2451–2472:

- `actualSeconds`
- `creditRevision`
- `creditSchemaVersion`
- `lastCreditOperationId`

لم يظهر أي كاتب تشغيلي لهذه الحقول في `index.html` عند SHA المدقق. ولم يظهر أي استخدام لـ`pendingFocusCommit` في الملف.

الفاحص `_validateTaskCreditFields(task)` يحقق حالياً:
- إذا غابت الحقول الأربعة كلها، يقبل المهمة باعتبارها Legacy.
- إذا ظهر أي حقل منها، يشترط وجود الأربعة كلها.
- `actualSeconds === null` يتطلب `actual === null`.
- إذا كان `actualSeconds` رقماً، يشترط عدداً صحيحاً آمناً غير سالب، وأن يكون `actual === floor(actualSeconds / 60)`.
- `creditRevision` عدد صحيح آمن غير سالب.
- `creditSchemaVersion === 1`.
- `lastCreditOperationId` إما null أو UUID بالشكل المتحقق منه في التعبير النمطي.

هذا فاحص جيد كجزء من العقد، لكنه **لا يهاجر البيانات، ولا يكتب الثواني، ولا يزيد revision، ولا يمنع كاتباً قديماً من حذف الحقول**. كما أن قبول غياب الحقول يجب أن يكون محصوراً في فترة ما قبل الترحيل مع حارس واضح؛ لا تترك نسخة قديمة تعيد كتابة سجل V2 بعد الترحيل وتسقط الحقول.

### 4.6 سجل جلسة V2 موجود كتحقق، لكن مسارات التسجيل ما زالت Legacy

### 4.7 انتهاء Pomodoro وتأكيد الجلسة أثناء الغياب يتجاوزان محرك اعتماد موحداً

- `_catchUp(backgroundReturn)` يبدأ عند 10375.
- داخل حلقة انتقال المراحل، يستدعي `_logSession(completedPhase, target, true, phaseEndAt)` مباشرة عند 10453.
- بعد التسجيل، يغيّر المرحلة وموضع الدورة في الذاكرة، ثم يحفظ حالة المؤقت قرب 10486–10518.

### 4.8 `sessionId` و`plannedDurationMs` لا يُنشآن عند بدء المرحلة

بحث الملف عند SHA المدقق أظهر:
- مراجع `sessionId` في فاحص V2، وفحوص التكرار في المحمل والحافظ فقط.
- مراجع `plannedDurationMs` في فاحص V2 فقط.
- لا إنشاء تشغيلي لهذين الحقلين عند بدء المرحلة.
- `startTimerForTask()` يعرّف `_beginNewSession()` قرب 13467؛ يحدد `now=Date.now()` ويضبط `taskId/mode/phase/baseElapsed/startedAt/sessionStartAt/running` ثم يحفظ `_saveFocusTimer()` قرب 13474. لا ينشئ UUID ولا يحفظ هدفاً ثابتاً للمرحلة.
- يجب توليد هوية المرحلة والهدف قبل التشغيل، وحفظهما بنجاح أولاً. إعادة الاستئناف يجب أن تحافظ على الهوية نفسها، أما الانتقال لمرحلة جديدة فينشئ هوية جديدة.

### 4.9 PWA: مراقبة فجوة الساعة ليست هي سياسة إغلاق المقطع عند الإخفاء

- مصدر الرتابة داخل الصفحة: `_readFocusMonotonicNow()` قرب 10007، ويقرأ `performance.now()`.
- `_getFocusTimerElapsedParts()` قرب 10228 يستخدم هذا المصدر، ويقارن عينة الساعة المدنية لاكتشاف الشذوذ.
- يوجد كشف لحالة النوم المحتملة في 10259–10282 عند ثبات performance تقريباً مع قفزة كبيرة في wall clock؛ عندها يوقف المؤقت عند آخر عينة موثوقة.
- توجد كذلك آلية fallback عند غياب/تراجع المصدر الرتيب قرب 10297 وما بعدها؛ راجعها بدقة حتى لا تستعمل `Date.now()` لإضافة زمن لا يثبت أنه نشط. الساعة المدنية للكشف فقط، لا لتعويض الفجوة.
- `visibilitychange` في `_setupVisibilityListener()` عند 13536: عند الإخفاء يستدعي `_saveFocusTimer()` فقط إذا كان المؤقت يعمل؛ لا يغلق المقطع النشط على آخر checkpoint موثوق ولا يوقف حالة التشغيل صراحة.
- مستمع `pagehide` عند 13567 يفعل الأمر نفسه: يحفظ المؤقت الجاري، ولا يغلق segment.
- مستمع `pageshow` الظاهر عند 9024 يضبط `_suppressBeforeUnload` فقط؛ ليس آلية استئناف زمنية كاملة.
- عند العودة إلى الواجهة، ينفذ `_onFocusTimerForegroundReturn()` قرب 13501 ثم مزامنة الساعة و`_catchUp(true)`. يجب أن يتحول ذلك إلى سياسة محافظة: لا تُحتسب فجوة الخلفية، ويطلب قرار المستخدم عند عدم إثباتها، ثم يبدأ مرجع رتيب جديد عند الاستئناف مع نفس sessionId للمرحلة نفسها.

اختبارات المتصفح لا تكفي وحدها لإثبات سلوك نوم الجهاز؛ يلزم اختبار Chrome Android وSafari iOS على أجهزة فعلية، مع إطفاء الشاشة وتعليق المتصفح والعودة إلى التطبيق وتغيير ساعة النظام.

### 4.10 إحصاءات الجلسات المضافة تحتاج مواءمة مع عقد التقارير

- `_focusSessionStatsForList()` يبدأ قرب 11431.
- يصنف كل سجل `phase === "work"` بوصفه عملاً، دون فصل صريح بين `mode === "pomodoro"` و`mode === "stopwatch"`. لذلك يجمع Stopwatch وPomodoro في total/count واحد.

- يجب حسم دلالة `partial`: هل `durationSec` يمثل حصراً مجموع المقاطع النشطة الموثوقة، أم يمثل المدة الإجمالية المشكوك فيها؟ لا تجمع مدة غير موثوقة. ويجب فصل Pomodoro work عن Stopwatch والاستراحات وفق التقارير المطلوبة في المواصفة.

### 4.11 النسخ الاحتياطية والاستيراد

## 6. عقد التصميم الذي لا يجوز تغييره ضمنياً

هذه النقاط محسومة في المواصفة، وأي تغيير لها يجب أن يكون قراراً معمارياً موثقاً لا اختياراً عارضاً أثناء البرمجة:

### نموذج الرصيد
- `actualSeconds` هو المصدر الأساسي؛ `actual` دقائق توافق مشتقة: `floor(actualSeconds / 60)`.
- `actualSeconds=null` يعني «لا يوجد رصيد مسجل»، وليس صفراً.
- الصفر المسجل `0` يختلف عن `null`.
- ترحيل `actual` إلى `actualSeconds` مرة واحدة وبعلامة إصدار، ولا تجمع السجلات التاريخية فوق الرصيد.
- إذا فشل استرداد معاملة Stopwatch قديمة، يمنع الترحيل وتبقى حماية الكتابة.
- كل كاتب لاحق يحدث `actualSeconds` و`actual` معاً.
- جلسة باعتماد موجب من `null`: يتحول الرصيد إلى العدد المعتمد.
- جلسة باعتماد صفري من `null`: يبقى null، لكن يزيد revision ويسجل operation ID.
- اعتماد صفري فوق رصيد صفر: يبقى 0، مع زيادة revision وتحديث operation ID.
- التصفير اليدوي الصريح يحول الرصيد إلى صفر مسجل، لا null.
- لا يعاد بناء الرصيد من آخر 500 سجل؛ حد السجلات للعرض وليس مصدر الحقيقة.

### نموذج الجلسة
- Session ID ثابت لكل مرحلة، ينشأ قبل تشغيلها ويحفظ أولاً.
- الإيقاف والاستئناف ضمن المرحلة نفسها يحافظان على sessionId.
- مرحلة جديدة تعني sessionId جديداً.
- `startedAt` و`endedAt` مدنيان للتوثيق والعرض فقط؛ لا يحسب منهما وقت العمل.
- `activeDurationMs` مجموع المقاطع النشطة الموثوقة فقط.
- `plannedDurationMs` يثبت مع بدء المرحلة ولا يتبدل بتغيير إعدادات المرحلة التالية.
- الفصل بين الزمن المقاس والزمن المعتمد إلزامي: `creditedSeconds` و`creditSource`.
- outcomes: `completed`, `ended_early`, `stopped`, `skipped`, `discarded`, `interrupted`; السجلات القديمة التي لا يمكن تفسيرها تظل Legacy ولا يعاد تأويلها.
- الاستراحات لا تضيف رصيداً.
- جلسات أقل من 60 ثانية لا تحذف بصمت؛ القرار explicit.
- لا تنتقل مرحلة بعد catch-up غير موثوق أو أثناء اعتماد معلق.

### التخزين والتزامن
- لا Event Sourcing شامل.
- لا إعادة كتابة Stopwatch بالكامل.
- لا IndexedDB الآن.
- لا مزامنة سحابية أو Flowtime أو أرشفة كاملة الآن.
- قفل Web Locks الحالي نفسه `timeTasksApp-stopwatch-transaction` يعاد استخدامه؛ لا قفل منفصل لـPomodoro.
- الغلاف العام async يكتسب القفل مرة واحدة، والدوال الداخلية Locked لا تطلبه ثانية.
- جميع الكتابات المتعارضة تتعاون مع القفل: المهام، الرصيد، الجلسات، حالة المؤقت، الترحيل، الاستيراد، الاستعادة، إعادة الضبط، والحفظ العام الذي يعيد تسلسل مصفوفة المهام.
- بعد امتلاك القفل، اقرأ أحدث التخزين وقارن baseline/revision. لا تكتب snapshot قديم.
- غياب Web Locks يعني fail closed للكتابات المتعارضة؛ لا fallback غير محمي.
- حالة المؤقت منفصلة عن حالة التخزين؛ لا تخلط running/paused مع pending/recovery_required.

## 7. ترتيب التنفيذ الملزم المقترح للخبير التالي

لا تنفذ كل شيء في commit واحد. قسّم العمل إلى commits صغيرة مستقلة، لكن لا تفعّل ترحيل الرصيد أو اعتماد Pomodoro قبل اكتمال البوابات السابقة.

### المرحلة A — تثبيت الأساس وإعادة جرد الكتّاب
1. أنشئ فرع تنفيذ من أحدث `codex/pomodoro-integrity-engine`، لا من PR #13 المتباعد.
2. احفظ SHA الأساس في وصف الفرع وملف سجل التنفيذ.
3. أعد جرد كل `saveData()` وجميع المستدعين غير المباشرين، وكل مواضع كتابة/حذف/استعادة `STORAGE_KEY`, `FOCUS_SESSIONS_KEY`, `FOCUS_TIMER_KEY` وأعلام المعاملات.
4. أعد جرد كل تعديل على `actual`، وكل مسارات إكمال/إلغاء/إحياء/حذف المهمة، وإغلاق اليوم، والتعديل اليدوي، وإنشاء المهام.
5. صنف كل كاتب إلى:
   - write path عادي يجب أن يكتسب القفل؛
   - دالة Locked لا تعمل إلا مع ملكية مثبتة؛
   - recovery/import/reset path ذي بروتوكول حصري موثق؛
   - test-only path معزول.
6. لا تخلط إصلاحات Android/الإشعارات مع أساس محرك الرصيد في هذا commit.

**مخرج المرحلة A:** جدول مصدر الحقيقة لكل كاتب/مستدعٍ، وخرائط call graph واختبارات قائمة. لا ترحيل ولا اعتماد جديد.

### المرحلة B — تأسيس طبقة الكتابة والقفل
1. صمم واجهة عامة async واحدة لاكتساب القفل المشترك، ونواة داخلية مثل `saveDataLocked()` لا تكتسب قفلاً.
2. ضع assertion/guard صريحاً في كل writer داخلي حساس ليثبت أن القفل مملوك.
3. لا تجعل `_storageWriteAllowed()` يوحي بامتلاك قفل؛ افصل شروط السماح عن ملكية القفل.
4. اجعل `saveData()` واجهة async تكتسب القفل ثم تعيد قراءة أحدث سجل **داخل القفل** قبل كتابة سجل المهام.
5. قرر سياسة stale snapshot: في الإصدار الأول ارفض بأمان وأطلب إعادة التحميل؛ لا تدمج تغييرات مصفوفة المهام كاملة بتخمين.
6. أدخل `persistDailyLog()` والكتابات المباشرة العادية في الطبقة نفسها.
7. أبقِ مسارات migration/reset/import/recovery في دوال داخلية Locked مع إثبات ملكية القفل وعدم وجود طلب متداخل.
8. حدّث **كل** المستدعين الـ21 حسب الجرد الجديد إلى await/Promise handling. لا تنسِ نماذج UI، callbacks، startup، recurring generation، shutdown، checklist، project actions، ومعاملات Stopwatch.
9. لا تعرض success أو تغلق UI أو تعتمد snapshot مرئية إلا بعد read-back verified.
10. إذا غاب Web Locks أو رفض request، لا تكتب عبر مسار قديم غير محمي.

**اختبارات مانعة للمرحلة B:**
- فشل/رفض القفل.
- عدم وجود Web Locks.
- منع deadlock عند استدعاء Locked helper من داخل القفل.
- جميع مستدعي saveData ينتظرون Promise فعلياً.
- تعطل الكتابة لا يعرض نجاحاً ولا يغلق النموذج.
- تبويبان: حفظ مهمة عادي مقابل اعتماد جلسة.
- تبويبان: persistDailyLog مقابل تعديل مهمة.
- تبويب قديم ينتظر القفل ثم يرفض stale snapshot.
- startup/migration/import/reset recovery لا تتداخل مع كتابة عادية.

لا تنتقل إلى ترحيل الرصيد إذا بقي أي كاتب متعارض خارج القفل.

### المرحلة C — جسر Stopwatch ثم ترحيل الرصيد
1. تحت القفل، استرد أي `pendingStopwatchTransaction` قديم قبل بدء الترحيل.
2. إذا كان هناك تعارض أو غموض أو فشل قراءة، أوقف الترحيل وكل الكتابات التابعة.
3. صمم معاملة ترحيل versioned/retry-safe؛ لا تضف الرصيد من الجلسات.
4. دلالة null والصفر يجب أن تحفظ حرفياً وفق القسم 6.
5. حدث جميع manual writers وtask lifecycle writers ليتعاملوا مع `actualSeconds`, `actual`, `creditRevision`, `creditSchemaVersion`, `lastCreditOperationId` معاً.
6. حدث معاملة Stopwatch الحالية واستردادها كجسر متوافق. لا تحذف `lastStopwatchTransactionId` ولا journal القديمة قبل انتهاء نافذة التوافق والتحقق.
7. أمنع إصدار التطبيق القديم من حفظ مجموعة المهام بعد الترحيل وإسقاط حقول الرصيد. إذا تعذر فرض ذلك، امنع الكتابة واطلب تحديث/إعادة تحميل صريح.
8. اختبر retry بعد كل نقطة كتابة في migration، وعدم double migration، وبيانات legacy، والرصيد null/0/موجب.

### المرحلة D — جلسات V2 ومحرك الاعتماد
1. أضف إلى حالة المؤقت `sessionId`, `plannedDurationMs`, وحقول قياس المقاطع الموثوقة اللازمة، مع تطبيع/تحقق/backup whitelist واضح.
2. قبل تشغيل المرحلة: أنشئ UUID، ثبت phase/task/target، احفظ، اقرأ وتحقق، ثم ابدأ clock. فشل الحفظ = لا يبدأ timer.
3. الإيقاف يضيف المقطع الموثوق مرة واحدة؛ الاستئناف يبدأ monotonic reference جديداً مع sessionId نفسه.
4. ابنِ V2 payload immutable قبل journal.
5. `pendingFocusCommit` سجل وحيد لكل عملية اعتماد، يحفظ session payload وtaskId والرصيد السابق/المستهدف الخام والحسابي وrevision وoperation ID وحالة المؤقت السابقة/التالية.
6. بروتوكول commit كما في المواصفة: journal + readback، task balance + marker/revision، session insert-if-absent، timer next-state، verify all، clear journal last.
7. حالات الاسترداد يجب أن تميز previous/target/null/zero/revision/marker ولا تستخدم مقارنة المبلغ وحدها.
8. غموض حالة أو محتوى sessionId مختلف = freeze writes ولا إعادة محاولة تلقائية.
9. وجه `_catchUp()`, `_showAwaySessionConfirmation()`, finish/stop/manual save/transition/notification actions إلى محرك الاعتماد نفسه.
10. لا تعتمد استراحة أو جلسة بلا مهمة على رصيد مهمة.
11. الجلسة غير الموثوقة لا تعتمد تلقائياً. لا تسجل completed دون بلوغ المخطط بزمن موثوق.

### المرحلة E — سياسة PWA والاختبارات الميدانية
1. في hidden/pagehide: أغلق segment عند آخر checkpoint موثوق واحفظ paused/interrupted/awaiting decision وفق التصميم.
2. عند visible/pageshow: لا تضف الزمن بين آخر checkpoint والعودة؛ لا تعتمد على wall clock للتعويض.
3. أعد تثبيت monotonic reference جديد عند resume مع بقاء sessionId للمرحلة نفسها.
4. راجع fallback من performance.now إلى Date.now؛ لا تجعل Date.now مصدراً لاعتماد وقت غير مثبت.
5. اختبر Chrome Android وSafari iOS فعلياً: إطفاء الشاشة، sleep، background suspension، tab reload، process kill، time-zone/time-of-day change، wall-clock backwards/forwards.
6. وثق نوع الجهاز/OS/browser، خطوات إعادة الإنتاج، والقيم المتوقعة/الفعلية، ولا تكتفِ بعبارة «اختبار ناجح».

### المرحلة F — التقارير والجاهزية
1. افصل Pomodoro work عن Stopwatch وعن short/long breaks.
2. قرر كيف يحتسب partial؛ لا تجمع ثوانياً غير مثبتة.
3. أبقِ حد الاحتفاظ 500 جلسة إن لم يعتمد تغيير آخر؛ الرصيد مستقل عنها.
4. وضح أن التقارير التاريخية نافذة محتفظ بها وليست أرشيفاً كاملاً.
5. شغل CI على SHA واحد محدد، وبعدها اختبار Android ميداني.
6. اطلب مراجعة مستقلة لمعالجة المعاملة والكتّاب والنسخ الاحتياطية.
7. لا تغير APP_VERSION ولا تصدر Release قبل اجتياز جميع البوابات.

## 8. مخطط حالات اختبار لا يجوز إسقاطه

### الرصيد والمخطط
- legacy task بلا حقول credit الأربعة.
- partial metadata (حقل أو أكثر فقط) => رفض.
- actualSeconds null مع actual null.
- actualSeconds null مع actual 0 => رفض.
- actualSeconds 0 مع actual 0.
- actualSeconds موجب مع actual=floor(seconds/60).
- اختلاف actual عن floor => رفض.
- revision سالب/غير آمن/غير صحيح => رفض.
- unknown creditSchemaVersion => رفض.
- UUID operation ID غير صالح => رفض.
- import/backup/export V1 وV2، وعدم استيراد journal داخلي.
- كتابات نسخة تطبيق قديمة بعد migration يجب أن تُمنع.

### الاعتماد
- اعتماد موجب من null.
- اعتماد صفري من null.
- اعتماد صفري من zero.
- تعديل يدوي يمسح الرصيد صراحةً (null/zero semantics).
- measured مقابل user_adjusted، مع فصل المقاس عن المعتمد.
- نفس sessionId ونفس payload = retry idempotent.
- نفس sessionId ومحتوى مختلف = conflict/freeze.
- اعتماد الجلسة مرتين لا يضيف رصيداً مرتين.
- لا يعتمد break أو unlinked session على task balance.
- session <60s لا تُحذف بصمت.

### الانقطاع وRecovery
حاكي فشل/إغلاق بعد كل حد كتابة:
1. بعد كتابة pendingFocusCommit.
2. بعد تحديث سجل المهمة والرصيد.
3. بعد إدراج سجل الجلسة.
4. بعد حفظ حالة المؤقت التالية.
5. بعد verify وقبل clear journal.
6. أثناء clear journal أو فشل readback.

لكل حالة: لا double credit، لا dropped session، لا تشغيل phase التالية قبل تأكيد السابقة، ولا تنظيف journal عند الغموض.

### التزامن
- task save مقابل focus commit.
- manual actual edit مقابل Stopwatch commit.
- daily log save مقابل task/focus commit.
- Pomodoro وStopwatch في تبويبين.
- import/restore/reset في وجود pending commit.
- startup migration مع pending legacy Stopwatch transaction.
- no Web Locks.
- nested call لا يطلب القفل مرة ثانية.
- stale tab لا يكتب full tasks array القديمة.
- all 21 saveData callers (أو العدد المعاد جرده) يترقبون Promise ويعرضون نتيجة صحيحة.

### PWA وAndroid
- pause/resume multiple segments مع sessionId ثابت.
- PWA reload لا يستخدم performance.now السابق.
- hidden/pagehide/sleep: لا يضاف وقت الخلفية غير المثبت.
- wall clock changed: يكتشف فقط، ولا يعوض.
- Android same boot identity يسمح باسترداد المرجع الصحيح.
- reboot مختلف يمنع احتساب الفترة بين الإقلاعين.
- permission denial وFGS startup failure حالتان منفصلتان.
- notification delivery failure لا تغير الرصيد.
